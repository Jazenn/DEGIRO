# Normalized import contract

The canonical import accepts Dutch and English Account and Transactions CSVs. It keeps the source fields, broker Asset identifier, currencies, source format, local date/time, normalized calendar date and diagnostics in each Transaction. `normalized_record` is an additive JSONB payload beside the existing database query columns; run the additive schema migration before using the updated database adapters. No live migration has been performed.

An order identifier is not an execution identifier. Execution identity version `execution-v2` hashes economic fields plus an occurrence number within an export. Identical-looking executions in one export remain separate. Repeating a complete export is idempotent. A smaller/larger overlapping multiplicity cannot prove whether an execution was added or omitted: the ingestion service returns `accepted=False`, retains `audit_transactions`, and makes no changes to its accepted identity state. Initialize a new service from the persisted accepted normalized Transactions to retain this behavior after restart. Existing legacy identities require reconciliation before migration; no automatic hash substitution can recover fills previously collapsed by an order-based identity.

Account statements distinguish external deposits/withdrawals, iDEAL reservation lifecycle movements and internal cash sweeps. Cash continuity is checked against successive reported balances within comparable ledger segments, without assuming the first row proves an opening balance of zero. Internal sweeps cross broker/bank subaccounts, so they end a comparable segment and carry an explicit continuity-unverified diagnostic. Blank sweep notifications retain their source evidence and `mutation_present=False`; they do not create a monetary posting. Blank required monetary postings and malformed nonblank amounts are rejected. Corrections, unexplained continuity gaps, unknown record classifications and unresolved same-minute buy/sell ordering require review. Review batches retain normalized source evidence and do not publish new Transactions. Invalid required numeric/date fields are rejected with source row context rather than converted into zero.

The broker's [report documentation](https://www.degiro.com/uk/helpdesk/tax/tax-treaties/which-reports-are-there-and-where-can-i-find-them) distinguishes account activity from the purchase/sale statement. It does not establish the exported timestamp timezone or DST convention. Local source timestamps therefore remain unverified, and the calculation report explicitly marks UTC cutoff eligibility unavailable. The retained legacy wall-clock filter is not verified UTC accounting and must not support finalized daily percentages.

The broker also documents [crypto ETPs](https://www.degiro.de/anlegen/krypto-tracker) which track crypto without direct ownership. A label containing Bitcoin/Ethereum, or a fractional quantity, cannot establish spot ownership, Asset kind or quote identity. Those fields remain explicitly unverified until evidence for the actual broker Asset is supplied. Non-EUR ledger amounts require dated FX and are held for review rather than summed into EUR cash. Unknown currencies remain labelled unknown rather than silently declared EUR.

Financial interpretation stays in the canonical Python calculation boundary. The additive [Decimal accounting read model](decimal-accounting-contract.md) now defines fee-inclusive FIFO, explicit opening/cost evidence and dated FX conversion. This identity migration does not certify those source facts or historical return eligibility.

# Reviewed Crypto Plan replacements

An Accepted Crypto Plan is immutable. New purchases do not change its original quantities. A holdings reduction, changed/missing imported execution or core mismatch suspends actionable stage review until the ledger and execution records are reconciled. Matching history and its canonical receipts stay recorded when an import corrects or reverses an execution; a correction never releases already consumed execution capacity or rearms a completed identity.

Choose **Review replacement** to retain the old plan on screen while reviewing a new core, quantities, levels and reason against current holdings. Preview and acceptance identify the old plan, plan version, Snapshot generation, reviewed broker terms, market history and shared execution version. Acceptance checks these again atomically. A conflicting edit requires reload and review. An unchanged request with an uncertain result retains its operation identity for a safe retry.

Resolve pending report remainders before replacement. **Cancel pending remainder** requires an explicit reason. Cancellation preserves the original report in an audit event and leaves matched allocations, actual execution facts and consumed capacity intact. It does not reverse a real Transaction or correct the canonical ledger. Import corrected source records through the existing canonical calculation workflow, then review their effects before accepting a replacement. A partial execution is retained against its old plan/stage identities; a replacement creates distinct identities and preserves the old accepted plan in history. BTC and ETH retain independent plan and execution versions.

Apply `hosted/crypto-replacement-schema.sql` after the execution schema only to an authorized staging destination; update `hosted/crypto-plan-schema.sql` there as part of the same reviewed migration. Grant the authenticated Worker EXECUTE on `hosted_review_crypto_replacement(jsonb)`, `hosted_cancel_crypto_report(jsonb)` and `hosted_read_crypto_report_events(text)` plus existing acceptance/execution functions. No browser mutation grants are required. Existing grants and private exports must be reviewed before migration.

Local operation/browser and isolated PostgreSQL checks use synthetic records. They establish behavior for pending partial reports, cancellation audit, replacement identity, stale execution versions, retries and independent coins. They do not establish real Neon concurrency, private correction/reversal reconciliation, deployment, provider coverage or cutover readiness. Those remain release gates in spec #40.
